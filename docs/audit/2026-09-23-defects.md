# The audit of 2026-09-23: confirmed defects

A read-only audit by ten independent auditors, one per subsystem, each told
to verify the code rather than trust the plan. Every defect an auditor
reported was then handed to a second, adversarial reader told to REFUTE it;
what is listed here survived that, with the severity the second reader
settled on. Refuted findings and ones judged "not a defect" are not listed.

How to use it: a fix cites the ID (`fixes audit QT-07`) in its commit message
and changes the entry's status line to FIXED with the commit, in the same
commit. PLAN.MD section 46 is the summary; this file is the detail. The
"suggested fix" is the auditor's suggestion, not a decision - check it.

Two defects the audit found were fixed before this register was written and
are not listed below: the licensed 12d customisation files were tracked in
git and pushed (untracked and ignored in 9c81f2f; removing them from the
pushed history needs a history rewrite, which is the owner's decision), and
the Workflow scratch worktrees were not ignored (454fc18).

## MOD - Entity model, commands, storage and selection

Belongs to: Phases 05-07 (sections 10-12).

### MOD-01 · high · Hiding or locking a parent layer does not hide, protect or stop editing of the entities on its children

`src/katana_cad/selection.cpp:63` · status: **OPEN**

**What goes wrong.** The layer contract says visibility and lock inherit down the tree (tables.hpp:60-61, PLAN.MD 5.1). The layer panel greys a child switched off by an ancestor (main_window.cpp:840-846). But isDrawn and isSelectable test only the entity's own layer flags (selection.cpp:63-72), and requireUnlockedLayer tests only the own lock (change_set.cpp:26-34). effectivelyVisible/effectivelyLocked have no caller except the panel. The viewport (viewport_widget.cpp:806), picking, box selection and the PDF plot all go through isDrawn/isSelectable.

**Failure scenario.** Layers 'design' and 'design/surface/tin1' with a line on tin1. Untick 'design' in the Layers dock: tin1's row turns grey ('switched off'), but the line stays drawn, pickable and plotted. Lock 'design' and run SELECT ALL then ERASE: the line on 'design/surface/tin1' is erased.

**Suggested fix.** Make isDrawn/isSelectable use layers.effectivelyVisible/effectivelyLocked (cache per frame or per layer to keep the draw loop cheap) and make requireUnlockedLayer use effectivelyLocked. Add a cad test that hides a parent and asserts the child's entity is neither drawn, picked nor editable.

*Survived the adversarial reader (confidence high).*

### MOD-02 · medium · Hiding a parent layer does not hide its children in either view (visibility inheritance is panel-only)

`src/katana_cad/selection.cpp:65` · status: **OPEN**

**What goes wrong.** cad::isDrawn uses layer->visible, and the 2D viewport (viewport_widget.cpp:806) and snapping (snapping.cpp:278) call it. The 3D scene builder (scene.cpp:366-369) checks only entity.visible and ignores layer visibility altogether. The layer panel greys children as hidden (main_window.cpp:842). The defect is in cad, but the claim it breaks (PLAN §5.1) is in this subsystem's plan section.

**Failure scenario.** Untick "design" in the layer tree while entities sit on "design/surface/tin1". The panel greys tin1, yet the 2D viewport still draws and snaps to its entities, and the 3D view draws them even when tin1 itself is unticked.

**Suggested fix.** isDrawn(layer, entity) needs the model to walk ancestors. Precompute a per-frame set of effectively hidden layers (a single pass over names()) and consult it in the viewport, snapping and scene paths rather than calling effectivelyVisible per entity, because layerAncestors allocates.

*Survived the adversarial reader (confidence high); severity changed from high to medium.*

### MOD-03 · medium · Edits are allowed on layers locked by an ancestor (lock inheritance not enforced by commands)

`src/katana_commands/change_set.cpp:33` · status: **OPEN**

**What goes wrong.** requireUnlockedLayer tests only the leaf layer's own `locked` flag. LayerDatabase::effectivelyLocked (tables.cpp:236-252), which implements the inheritance PLAN §5.1 claims is delivered, is used only for a tooltip (main_window.cpp:845). The same leaf-only rule is in cad::isSelectable (selection.cpp:71), so ancestor-locked entities are also pickable.

**Failure scenario.** Layers "design" (locked=true) and "design/kerb" (locked=false), one line on "design/kerb". stack.execute(moveEntities({id}, Vec2(1,0))) succeeds and the line moves, although effectivelyLocked("design/kerb") is true and the panel says "Locked here or by a parent layer". Deleting it and SET_LAYER both succeed too.

**Suggested fix.** In requireUnlockedLayer keep the NotFound branch, then use model.layers.effectivelyLocked(layerName) instead of layer->locked. Add a test in test_commands.cpp that locks a grandparent and expects CommandRejected for MOVE/DELETE/SET_LAYER. Change cad::isSelectable the same way.

*Survived the adversarial reader (confidence high); severity changed from high to medium.*

### MOD-04 · medium · LayerDatabase::hasChildren misses children when a sibling sorts between parent and child

`src/katana_entity/tables.cpp:211` · status: **OPEN**

**What goes wrong.** hasChildren looks only at upper_bound(name) and assumes the next key is a child if any child exists. Under std::less<string>, '-' (0x2D), '.', space and other punctuation sort below '/' (0x2F), so "ROAD-EDGE" lands between "ROAD" and "ROAD/CL". LayerDatabase::remove (:123) and the GUI's branch-or-leaf decision (main_window.cpp:1231) both depend on it.

**Failure scenario.** Layers "ROAD", "ROAD-EDGE", "ROAD/CL" with no entities on "ROAD". The GUI Delete on "ROAD" skips the tree confirmation and runs deleteLayer("ROAD"), and remove() erases it, leaving "ROAD/CL" orphaned (shown as a root item "CL"). After save and reopen, applyToModel's layers.add("ROAD/CL") recreates "ROAD" with default white, visible and unlocked attributes, so the deleted layer comes back.

**Suggested fix.** auto it = layers_.lower_bound(std::string(name) + kLayerSeparator); return it != layers_.end() && isLayerUnder(it->first, name); All "name/..." keys are contiguous under that prefix. Add a test with a '-' sibling, and correct the pre-order comments in layer_path.hpp:18-20, tables.hpp:66-67 and tables.cpp:157-159.

*Survived the adversarial reader (confidence high).*

### MOD-05 · low · Rollback failures are swallowed

`src/katana_commands/command_stack.cpp:213` · status: **OPEN**

**What goes wrong.** Transaction::execute discards each rollback undo() Status with (void). ChangeSetCommand::execute's fail lambda does the same (change_set.cpp:162). PLAN §36 forbids silent failures, and a failed rollback leaves the model half-applied, with no events published and so a spatial index out of step.

**Failure scenario.** A transaction step fails and one of the earlier steps' undo() returns an error, for example CreateLayerCommand::undo when a later step has added a child layer under it. The user sees only the original step error while the model keeps part of the transaction.

**Suggested fix.** Collect rollback failures and append them to the returned error's context ("rollback also failed: ..."). Log them at error level.

### MOD-06 · low · Commands that change nothing are accepted and recorded

`src/katana_commands/entity_commands.cpp:91` · status: **OPEN**

**What goes wrong.** modifyEach always pushes a modify entry, so a change set whose images equal the current entities is non-empty and passes. docs/model.md:218 says such a command is CommandRejected. UpdateLayerCommand does check equality (layer_commands.cpp:58-61).

**Failure scenario.** SET_COLOR to the entity's current colour, MOVE by (0,0) or RENAME_PROPERTY a->a each add an undo step and set isModified() on an unchanged drawing.

**Suggested fix.** In ChangeSetCommand::validate, drop modify entries equal to the current entity and reject if nothing is left.

### MOD-07 · low · CREATE_LAYER / RenameLayer undo, and Transaction rollback, leave implicitly created ancestor layers behind

`src/katana_commands/layer_commands.cpp:37` · status: **OPEN**

**What goes wrong.** LayerDatabase::add creates missing ancestors (tables.cpp:92-95) and renameSubtree creates the new parents (:343-346), but CreateLayerCommand::undo removes only the named layer and RenameLayerCommand::undo only renames back. Neither undo is exact, which breaks command.hpp's contract (undo restores the exact prior state). Through Transaction::execute's rollback (command_stack.cpp:211-214), a FAILED command leaves the model changed: CommandStack reports that the model is unchanged, no history entry exists to undo it, and isModified() stays false.

**Failure scenario.** GUI import (main_window.cpp:1627-1640) whose layersNeeded = {"roads/main"}, where a later entity step fails validation. The transaction rolls back and reports failure, but layer "roads" stays in the model with no undo entry and no dirty flag. In the simple case, CREATE_LAYER "a/b" on a fresh drawing followed by Undo leaves "a".

**Suggested fix.** In execute(), record the set of layer names that did not exist before (diff names() before and after the add or rename), and remove them deepest-first in undo(). Add tests for nested create, undo and redo, and for a failing transaction, asserting on layers.names() as well as on entities.

*Survived the adversarial reader (confidence high); severity changed from medium to low.*

### MOD-08 · low · Branch and table deletions are not flagged destructive

`src/katana_commands/layer_commands.cpp:137` · status: **OPEN**

**What goes wrong.** DeleteLayerTreeCommand does not override isDestructive() (DeleteLayerCommand does, :92). DeleteItemCommand<T> (table_commands.cpp:326-363) is never destructive either, including deleteAlignment, which has no in-use guard (:215-220) and discards designed PI and PVI data. command.hpp:40-41 and PLAN §31 make this flag the confirmation gate for AI commands.

**Failure scenario.** A future AI or Transaction path running deleteLayerTree("design") or deleteAlignment("road") reports isDestructive()==false, so no user confirmation is requested, while DELETE_LAYER of a single empty leaf does ask.

**Suggested fix.** Return true from DeleteLayerTreeCommand::isDestructive and DeleteItemCommand::isDestructive, at least for alignments. Add assertions next to test_commands.cpp:461.

### MOD-09 · low · Several commands' validate() says OK for changes their execute() then refuses

`src/katana_commands/table_commands.cpp:112` · status: **OPEN**

**What goes wrong.** TablePolicy<Linetype>::updatable returns {} although LinetypePolicy::checkUpdate (tables.cpp:550-557) forbids giving "continuous" a pattern. CreateLayerCommand::validate (layer_commands.cpp:21-30) skips validateLayerPath and the line-weight check. DeleteLayerCommand::validate (:94-108) skips the has-children check. A caller that pre-validates (Rule 2's validation step) is told the command is fine.

**Failure scenario.** updateLinetype(Linetype{"continuous","",{{1.0},{-0.5}}})->validate(ctx) returns OK, and execute returns InvalidArgument. createLayer(Layer{"a//b"})->validate(ctx) returns OK, and execute fails.

**Suggested fix.** Have the command validate() call the same table predicates (expose NamedTable::canUpdate / LayerDatabase::canAdd), or delegate to the policy rather than restating it in TablePolicy.

### MOD-10 · low · Geometry that passes validation can make every save fail (text override not UTF-8 checked; length and vertex caps enforced only by the blob writer)

`src/katana_entity/entity_geometry.cpp:296` · status: **OPEN**

**What goes wrong.** Validator::operator()(DimensionGeometry) never calls isValidUtf8(textOverride), and no validator caps a string at 1,000,000 bytes or a polyline at 10,000,000 vertices. geometryToBlob enforces all three (geometry_blob.cpp:67-76, :181-186), and ProjectStore::save returns that error without the entity id (project_store.cpp:1185-1188, and the same for properties at :1189-1196).

**Failure scenario.** createDimension({p0, p1, 1.0, "\xE9"}) or createEntities with a 1.2 MB TextGeometry is accepted and drawn. Every later save fails with InvalidArgument "text is not valid UTF-8" or "text is too long to store", with no entity id in the message, so a 50k-entity drawing cannot be saved and the user cannot find the culprit.

**Suggested fix.** Add the UTF-8 check for textOverride in the Validator. Move kMaximumStringBytes and kMaximumVertices into a header shared by validate() and the blob code. In save(), wrap encoding failures with "entity id=<id>" as the insert failure path already does.

*Survived the adversarial reader (confidence medium); severity changed from medium to low.*

### MOD-11 · low · Text extents count UTF-8 bytes as characters

`src/katana_entity/entity_geometry.cpp:319` · status: **OPEN**

**What goes wrong.** textBaseline uses text.text.size(), which counts bytes, although the comment and docs say 0.6 x height per character. Non-ASCII labels get baselines too long, by 2x for accented Latin runs and 3x for CJK. That inflates boundingBox and moves distanceTo past the visible end of the text.

**Failure scenario.** The 5-character label "Ωμέγα" (10 bytes) at height 1 gets a 6.0-unit baseline instead of 3.0, so clicking 4 units to the right of the drawn text still picks it.

**Suggested fix.** Count code points, i.e. bytes that are not UTF-8 continuation bytes; the text is already guaranteed valid UTF-8.

### MOD-12 · low · Layer names are not UTF-8 validated, contrary to the model-wide invariant

`src/katana_entity/layer_path.cpp:23` · status: **OPEN**

**What goes wrong.** validateLayerPath rejects control characters, whitespace and '.'/'..', but not invalid UTF-8, while every other named record goes through detail::validateName (validation.cpp:15). entity.hpp:33 says every string that reaches the model is checked. Layer linetype, hatch and dimension-style reference strings and Linetype, HatchPattern, Alignment and PropertyDefinition descriptions are unchecked as well.

**Failure scenario.** LAYER NEW Caf\xE9 typed on a CP1252 console is accepted. entityToJson of an entity on that layer then returns Internal "value could not be written as JSON", which breaks the structured-API path this serialiser exists for.

**Suggested fix.** Call isValidUtf8 in validateLayerPath, and on descriptions in each table validator.

### MOD-13 · low · Renaming a layer subtree can create layer names that fail validation, making the project unopenable

`src/katana_entity/tables.cpp:307` · status: **OPEN**

**What goes wrong.** renameSubtree validates only `to` (:289) and its ancestors (:322-326). The rewritten descendant names are never checked against kMaximumLayerDepth (16) or kMaximumLayerNameLength (512) and are inserted directly (:347-350). RenameLayerCommand::validate (layer_commands.cpp:207-226) also checks only to_. ProjectStore::save's validateContents checks only that names are non-empty (project_store.cpp:291-296), but load goes through LayerDatabase::add, which validates.

**Failure scenario.** A 16-level branch "a/1/2/.../15" (valid) renamed "a" -> "p/q/a" from the GUI (Rename) succeeds and the deepest layer now has 18 levels. Save succeeds. Reopening fails in applyToModel with InvalidArgument "layer name is nested too deeply", so the project cannot be opened. The same happens when a rename lengthens a path past 512 characters.

**Suggested fix.** In the pre-check loop at :313, also run validateLayerPath(after) for every mapping entry before anything moves. Make validateContents run validateLayerPath on every layer so save refuses what load would refuse.

*Survived the adversarial reader (confidence high); severity changed from medium to low.*

### MOD-14 · low · The DIMRND floor compares a display-unit step with a model-unit tolerance

`src/katana_entity/tables.cpp:435` · status: **OPEN**

**What goes wrong.** roundTo applies to the value AFTER unitScale (dimension_text.cpp:88-99), so it is in display units, but it is compared against tolerance::kGeometric, which is in model units.

**Failure scenario.** With unitScale=1e-6 (megametres) and roundTo=1e-8 Mm (1 cm of ground), the style is refused as finer than the geometric tolerance. With unitScale=1000 the check bites only at 1e-7 mm, i.e. 1e-10 m.

**Suggested fix.** Compare roundTo / unitScale with kGeometric.

### MOD-15 · low · A property definition with a non-finite default saves successfully and makes the project unopenable

`src/katana_entity/tables.cpp:778` · status: **OPEN**

**What goes wrong.** PropertyDatabase::define checks only that the default's type matches. It does not check finiteness or UTF-8, although PropertyDatabase::validate enforces both for entity values (:816-831). save() serialises the default through propertiesToJson (project_store.cpp:1011-1016), nlohmann writes NaN or Inf as null, and validateContents never looks at definitions. On load, propertiesFromJson rejects null (serialization.cpp:150-161), so the whole load fails. This is the same class of bug as the metadata-NaN regression that change_set.cpp:57-69 already fixed.

**Failure scenario.** model.properties.define({"level", PropertyType::Real, "", PropertyValue{NaN}}), then Document::save succeeds. Every later Document::open fails with ParseFailure "property values must be boolean, number or string", and no recovery is offered because the code is not DatabaseFailure. Today only library/API callers can reach this; there is no UI verb for definitions.

**Suggested fix.** In define(), when defaultValue is set, call the same finiteness and UTF-8 checks as validate(), and check the name and description. Have validateContents validate property definitions.

*Survived the adversarial reader (confidence medium); severity changed from medium to low.*

### MOD-16 · low · The backup collision loop recomputes the timestamp, so a later backup can rank as older

`src/katana_storage/project_store.cpp:826` · status: **OPEN**

**What goes wrong.** utcTimestamp(true) is called again inside the suffix loop, so a backup that collides at millisecond N can be written as "<N+1>-1" if the clock ticks during the loop. A backup made later in millisecond N+1 is then named "<N+1>" (sequence 0), and backupsNewestFirst (:466-471) ranks the earlier file above it.

**Failure scenario.** Backups A at t=123 and B at t=123 (renamed while the clock moves to t=124, giving "124-1"), then C at t=124 ("124"). listBackups() returns B before C, so recover() restores B instead of the newer C, and pruning with keep=N can delete C first.

**Suggested fix.** Compute the stem once before the loop and append only the suffix inside it.

### QT-02 · high · Styles and Linetypes 'Save Changes' silently rewrites the linetype and symbol of every 12d-imported style

`src/katana_qt/style_manager.cpp:604` · status: **OPEN**

**What goes wrong.** The 12da importer gives each style linetype = symbol = the 12d linestyle name, e.g. 'SEWR Manhole Cover' (domain_import.cpp:286, 299), and applySurveyCodes does the same with library names (survey_coding.cpp:183, 189). **Suggested fix.** When loading a style, insert its linetype or symbol name into the combo if it is absent (or use editable combos filled from model.linetypes, the loaded library and symbolNames). Add a test that Save Changes on an unedited form leaves the style byte-identical.
